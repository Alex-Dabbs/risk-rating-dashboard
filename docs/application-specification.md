# Northstar GRC Dashboard — Application Specification

## 1. Purpose

Northstar GRC is a browser-based dashboard for manually entering and reviewing security assessment findings associated with ISO 27001:2022 control areas. It gives executives a concise view of risk and remediation status while giving analysts a register for maintaining finding details, evidence notes, and a dated action history.

The dashboard is an interactive recordkeeping and overview tool. It does not ingest or extract information from the Executive Summary, Security Assessment, or Security Findings & Remediation Tracking Report. Users enter and maintain the information directly in the application.

### Current scope

- View an overview of finding counts, overdue findings, open findings, and critical-risk findings.
- View the distribution of findings across Low, Medium, High, and Critical risk levels, with an optional year filter.
- View the manually assessed residual-risk distribution and the number of findings not yet assessed.
- Review a prioritized Needs Attention list.
- Add, search, filter, sort, and update findings.
- Open a finding to review or edit its details, record evidence, and post or delete remediation updates.
- Switch between light and dark themes and use desktop, tablet, or narrow-screen layouts.

## 2. User personas

### Executive overview — CISO or security leader

**Goal:** Quickly understand the organization's current security-finding exposure and where leadership attention may be needed.

**Primary tasks:**

- Review total, overdue, open, and critical-risk finding counts.
- Compare the Low, Medium, High, and Critical distribution, optionally for a selected year.
- Scan the Needs Attention list for findings that remain open.
- Open a finding when more context is needed.

**Information priorities:** High-level risk, remediation urgency, ownership, and status. The overview is intended to make the current register understandable at a glance; its numbers are derived from the findings currently saved in that browser.

### Analyst findings — GRC, security, or control owner analyst

**Goal:** Maintain accurate assessment records and document remediation activity and control evidence.

**Primary tasks:**

- Add findings with a unique ID assigned by the application.
- Search findings by ID and narrow the register by risk or status; sort by due date, risk, last-updated date, or ID.
- Open a finding to review and edit its description, ISO control area, risk, owner, dates, status, and evidence.
- Record evidence status and describe evidence used to validate the control.
- Post dated remediation updates attributed to the current demonstration user, or remove an update.
- Track the current status and last-updated date.

**Information priorities:** A complete record, a clear accountable owner, a due date, evidence, and a traceable remediation narrative.

## 3. Application behavior and rules

- Finding IDs use the format `YYYY-NNNN`, such as `2026-0001`. The ID is assigned when a finding is created and is not editable in the finding editor.
- Finding descriptions must contain at least 30 characters when a finding is created or saved after editing.
- Search matches the unique finding ID only. Risk and status filters and the available sort options operate on the register separately.
- Overdue means the remediation due date is earlier than the current date and the finding is not Closed.
- The Needs Attention panel lists up to three non-Closed findings, ordered by due date.
- The risk distribution and risk counts are derived from the risk value on each finding. The chart's year filter uses the year in `dateIdentified`.
- Residual risk is recorded separately as an analyst-entered rating after controls are considered. It may also be marked Accepted when a finding was compliant in the original assessment and no remediation-based residual rating applies. It is not inferred from inherent risk, status, or evidence; blank values are shown as Not assessed and excluded from the residual-risk distribution.
- A finding's `lastUpdated` date changes when the finding is edited, its status changes, or an update is posted or deleted.
- Update comments are displayed in reverse chronological insertion order and include author and posting time.

## 4. Data model

### Finding

One record in the findings register.

| Field | Type / format | Required | Description |
|---|---|---:|---|
| `id` | String, `YYYY-NNNN` | Yes | Unique finding identifier. Generated by the application and immutable through the editor. |
| `description` | String | Yes | Narrative describing the finding; minimum 30 characters. |
| `controlArea` | String | Yes | ISO 27001:2022 control reference, for example `A.5.15` or `A.5.24-A.5.26`. |
| `dateIdentified` | String, `YYYY-MM-DD` | Yes | Date the finding was identified. |
| `dueDate` | String, `YYYY-MM-DD` | Yes | Remediation due date. |
| `risk` | Enum: `Low`, `Medium`, `High`, `Critical` | Yes | Assessed risk criticality. New findings default to `Medium`. |
| `residualRisk` | Empty or enum: `Low`, `Medium`, `High`, `Critical`, `Accepted` | No | Analyst-entered assessment of risk remaining after controls are considered. `Accepted` records a finding with no applicable remediation-based residual rating. Empty means Not assessed. |
| `residualRiskRationale` | String | No | Brief explanation supporting the residual risk rating or Accepted decision. |
| `owner` | String | Yes | Accountable owner or department. |
| `status` | Enum: `Open`, `In Progress`, `Under Review`, `Closed` | Yes | Current remediation status. New findings default to `Open`. |
| `evidence` | Enum: `No Evidence Provided`, `Evidence Provided`, `Evidence Validated` | Yes | Evidence-review status. New findings default to `No Evidence Provided`. |
| `evidenceDetails` | String | No | Free-text description of the evidence used to validate the control. Empty when no notes have been recorded. |
| `lastUpdated` | String, `YYYY-MM-DD` | Yes | Date the finding record was most recently touched. |
| `updates` | Array of Update | Yes | Remediation or progress comments associated with this finding. Defaults to an empty array. |

### Update

An action or progress comment nested in a finding's `updates` array.

| Field | Type / format | Required | Description |
|---|---|---:|---|
| `comment` | String | Yes | User-entered remediation action or progress note. |
| `author` | String | Yes | Display name attached to the update. The public demo uses `Demo User`. |
| `createdAt` | ISO 8601 timestamp | Yes | Date and time the update was posted. |

### Browser preferences and storage

| Key | Stored value | Purpose |
|---|---|---|
| `grc-findings` | JSON array of Finding records | Persists findings and their nested updates in browser local storage. |
| `grc-theme` | `light` or `dark` | Persists the selected theme in browser local storage. |

No server-side database or separate Company entity is currently implemented. The overview's company identity (`Ceraphin Energy Solutions`) is configured directly in the interface, and the update author (`Demo User`) remains a demonstration value. The initial five records are synthetic sample data used to populate a new browser profile. Replace them with authorized assessment data before use.

## 5. Current implementation and limitations

- **Client:** React single-page application, built and served with Vite; styles are maintained in CSS.
- **Persistence:** Browser local storage. Records are available only in the same browser profile and on the same device where they were entered. Clearing site data removes them. There is no synchronization, backup, access control, or central audit store.
- **Authentication and attribution:** No sign-in or role system exists. `Demo User` is a fixed demonstration author, not an authenticated identity. Users of the same browser can edit the same locally stored records.
- **Import and export:** The app does not currently import the three supporting documents or provide a data import/export workflow.
- **Audit history:** Updates provide a dated comment history, but updates can be deleted and edits to finding fields do not retain before/after values. This is not an immutable audit log.
- **Company identity:** The displayed company name is currently hard-coded rather than configured as a data entity.

These constraints are appropriate to the current local prototype. Shared use, authenticated attribution, centralized retention, or audit requirements would require a backend and corresponding access and data-management design.

## 6. Product terminology

- **Finding:** A recorded issue or observation associated with an ISO control area.
- **Evidence status:** The controlled assessment value describing whether evidence is absent, provided, or validated.
- **Evidence details:** Analyst-entered text describing what evidence was used to validate the control.
- **Update:** A dated and attributed progress comment attached to a finding.
- **Overdue finding:** A non-Closed finding whose remediation due date has passed.
